# Описание реализации: приложение «Фото по лицу» для мероприятий

Nov 21, 2026 · @Yermek

Реализация идеи из [product-vision.md](product-vision.md): архитектура, данные, стек, процесс разработки и требования к устройствам.

## Технические принципы

- Всё на устройстве, без сервера и интернета; никакой аналитики и краш-репортов с данными
- Данные только на внешнем носителе (microSD/USB): выбор папки через `ACTION_OPEN_DOCUMENT_TREE` («выбор папки»), во внутреннюю память устройства ничего не пишется; без носителя приложение не работает
- Данные о лицах зашифрованы ключом события и исключены из резервного копирования в облако
- Вектор пользователя удаляется сразу после сессии
- Доступ ко всем фото устройства (`READ_MEDIA_IMAGES`, «чтение изображений») не запрашивается
- Стек: Kotlin Multiplatform + Compose Multiplatform (см. раздел «Стек и кроссплатформенность»)

## Архитектура и данные

**Конвейер A — индексация снимков (фоном, WorkManager):**

1. Новые файлы в папке события на носителе (инкремент по имени и дате изменения).
2. Декодирование уменьшенной копии (\~1024 px, `ImageDecoder` с целевым размером), учёт EXIF-поворота.
3. Детекция лиц и 5 ключевых точек; для фото с мелкими лицами — повтор в большем разрешении.
4. Выравнивание и кроп 112×112, отсев мелких и размытых лиц.
5. Эмбеддинг (128–512 float), нормализация L2.
6. Запись в зашифрованную БД на носителе: фото → лица → bbox + вектор.

**Конвейер B — сессия пользователя:**

1. CameraX (ImageAnalysis) → детекция и трекинг лиц в потоке.
2. Усреднение эмбеддинга по 5–10 кадрам на каждого смотрящего.
3. Косинусный поиск перебором по БД события; два порога: «точно» и «возможно» (отдельная группа).
4. Расширение запроса: повторный поиск по центроиду уверенных совпадений.
5. Показ, выбор, печать / QR-выдача; удаление вектора пользователя.

**Хранение на носителе:**

| Данные | Формат | Удаление |
| --- | --- | --- |
| Фото события | JPEG/HEIC в папке события | Не удаляются приложением |
| Индекс лиц (bbox + векторы) | SQLite + SQLCipher, ключ события в Android Keystore | «Завершить мероприятие» + уничтожение ключа |
| Вектор пользователя | Только в памяти | После «Готово» |
| Списки на печать | Идентификаторы фото, без биометрии | Вместе с индексом |

## Стек и кроссплатформенность

Выбран Kotlin Multiplatform (KMP) с Compose Multiplatform: общий код логики, ML-конвейера и UI для Android и iOS, платформенные части — через `expect/actual` («ожидаемая/фактическая реализация»). Compose Multiplatform для iOS стабилен с версии 1.8.0 (май 2025). Первый выпуск — Android, iOS добавляется платформенными адаптерами без переписывания ядра.

| Слой | Общий код (commonMain) | Android | iOS |
| --- | --- | --- | --- |
| UI | Compose Multiplatform | — | — |
| Логика, навигация, состояние | Kotlin, coroutines | — | — |
| Детекция и эмбеддинги лиц | Модели YuNet + AuraFace или SFace (выбор по тесту точности), пре-/постобработка, поиск | Рантайм: ONNX Runtime | ONNX Runtime |
| БД индекса | SQLDelight или Room KMP + SQLCipher | — | — |
| Камера | Интерфейс потока кадров | CameraX | AVFoundation |
| Внешний носитель | Интерфейс хранилища | SAF (`ACTION_OPEN_DOCUMENT_TREE`) | `UIDocumentPicker` + security-scoped URL |
| Ключ шифрования | Интерфейс хранилища ключей | Android Keystore | Keychain |
| Печать | Раскладка страниц (PDF) | PrintManager | AirPrint (`UIPrintInteractionController`) |
| Фоновая индексация | Очередь задач | WorkManager | В переднем плане (фон в iOS ограничен) |
| Раздача по QR | HTTP-сервер Ktor (CIO), генерация QR | Точка доступа или общая Wi-Fi | Только общая Wi-Fi (программно точку доступа не создать) |

**Принципы, снижающие затраты на перенос:**

- Детекция и распознавание — на одних и тех же моделях и одном рантайме на всех платформах, без ML Kit и Apple Vision: одинаковые векторы и пороги.
- Все платформенные API скрыты за интерфейсами в commonMain; новая платформа = набор адаптеров (камера, хранилище, ключи, печать, фон).
- Формат БД и файлов на носителе одинаков — носитель читается на любой платформе.

**Альтернативы (не выбраны):**

| Стек | Плюсы | Минусы |
| --- | --- | --- |
| React Native + VisionCamera + react-native-fast-tflite | TypeScript; готовые плагины для обработки кадров и TFLite | Критичные части (фоновая индексация, SAF, печать) всё равно на нативе; зависимость от сторонних плагинов |
| Flutter | Зрелый общий UI | Dart; камера + ML в реальном времени требуют нативных плагинов |
| Чистый натив (Kotlin + Swift) | Максимальная производительность | Два кода — максимальные затраты на перенос |

## Агентская разработка

Код пишут AI-агенты, поэтому архитектура должна позволять агенту собрать, запустить и проверить каждое изменение без участия человека и без физического устройства.

**Требования к проекту:**

- **JVM/Desktop-таргет для тестов.** Ядро (детекция, эмбеддинги, поиск, БД, раскладка печати) собирается и тестируется на JVM через ONNX Runtime для Java — агент гоняет его на Windows без эмулятора. Это ещё один довод за единый рантайм без ML Kit / Apple Vision.
- **Эталонный набор данных в отдельном приватном репозитории** (биометрия реальных людей, основной репозиторий публичный; см. [testdata.md](testdata.md)): фото с разметкой «кто на каком фото» и селфи-запросы (лица с разрешением или синтетические). Тест точности с порогами recall/precision — критерий приёмки любого изменения ML-кода.
- **Камера за интерфейсом:** фейковый источник кадров из видеофайла для тестов сессии и для эмулятора.
- **Тонкие платформенные адаптеры.** Вся логика — в commonMain; в androidMain/iosMain только вызовы системных API. Адаптеры проверяются инструментальными тестами на эмуляторе.
- **Всё через CLI:** `./gradlew build`, `./gradlew jvmTest`, `./gradlew connectedAndroidTest` («сборка», «тесты на JVM», «тесты на эмуляторе»); линтеры ktlint + detekt; UI-скриншот-тесты (Roborazzi или Paparazzi) для проверки экранов без устройства.
- **CI** (GitHub Actions): сборка, тесты и тест точности на каждый PR; iOS-сборка — на macOS-раннере (локально на Windows iOS не собирается).
- **Инструкции для агентов в репозитории** (CLAUDE.md / AGENTS.md): структура модулей, команды сборки и тестов, правила (никаких сетевых вызовов, данные только на внешнем носителе), фиксированные версии библиотек.
- **Маленькие модули с чёткими интерфейсами** (`:core:ml`, `:core:db`, `:core:storage`, `:feature:session`, `:feature:print`) — агенты работают параллельно в отдельных git worktree без конфликтов.

**Риск стека для агентов:** по KMP и Compose Multiplatform для iOS примеров кода меньше, чем по Android или React Native, — агенты чаще ошибаются в Gradle-конфигурации и `expect/actual`. Компенсация: старт с официального шаблона KMP-проекта, зафиксированные версии в version catalog, примеры паттернов в CLAUDE.md.

## Производительность и требования

- Минимум: Android 10+, 4 ГБ ОЗУ, слот microSD или USB-OTG; рекомендуется 6–8 ГБ.
- Расчёт на CPU (ONNX Runtime, при необходимости int8-квантизация моделей); GPU и NNAPI — как ускорение при наличии.
- Индексация: оценочно 30–100 мс на фото; порция 500 фото — 1–2 мин. Оценка верна для лёгкой модели эмбеддингов (SFace); AuraFace (ResNet100, ~24 GFLOPs на лицо) заметно медленнее, выбор модели — по тесту точности и замерам на устройствах.
- Сессия пользователя: распознавание менее 1 с, поиск по 50 тыс. лиц — десятки миллисекунд.
- Индексация не запускается во время сессии пользователя и идёт порциями (термотроттлинг).
- Цифры проверить прототипом на 2–3 целевых устройствах.
